# Internal audit JSON contract

`audit.json` and `history/audit-*.json` contain the `AuditReport` dataclass
graph with `schema_version: 4`. The field declarations in `models.py` define
the stored shape; `audit.load_audit` reconstructs and validates those models.
Each document describes one container. Metadata, binaries, issues, statistics,
and scan/toolchain provenance are top-level fields. A batch keeps independent
per-container audit files; its progress records track execution outcomes and
published paths without copying the evidence.

Image identity records the vendor image name, image build release, CPE and PURL
lists, separate layer product contexts, and explicit CSAF product-ID pins. Older audit
files must be regenerated; the reader accepts only the current contract.

The saved audit supplies all scan evidence shown in reports. Publication saves
staged JSON, validates it, and renders text from the reconstructed models.
Successful and strict failed scans use this same path; terminal summaries also
reload the saved audit. Current configuration, identity sidecars, caches, and
extracted files do not supplement recorded evidence when rendering. CSAF
comparisons additionally consume supplied advisory documents and can explicitly
select an identity JSON override or a product-ID pin; their effective identity and
override source are recorded separately from the unchanged audit fingerprint. Extraction stores
RPM observations separately in the container metadata sidecar.

## Field rules

- Every declared evidence field is required, including constructor defaults,
  empty strings/collections, and nullable fields. `Module.replace` is always
  present; an absent replacement is null. An unknown image is an `ImageIdentity`
  object with empty string and collection fields.
- JSON keys match dataclass field names. Nested dataclasses are objects;
  lists and tuples are arrays. Properties and report-processing dataclasses
  are not serialized.
- Input must be a UTF-8 JSON object. Duplicate keys, missing or unknown fields,
  non-string object keys, and wrong types fail. Values are never coerced.
- Integers must be nonnegative integers; booleans are not integers.
  Floating-point numbers, `NaN`, and infinities fail.
- JSON object order and whitespace are irrelevant. Binary paths are sorted;
  binaries are ordered by minimum path and issues by path/stage. The reader
  rejects arrays that differ from their canonical serialization. Other evidence
  arrays, including layer history and recorded comparisons, retain their order.

## Stored evidence

| Dataclass | Stored fields |
| --- | --- |
| `AuditReport` | `schema_version`, `metadata`, `binaries`, `issues`, `stats`, `go_command`, `go_tool_version`, `producer_name`, `producer_version`, `govulncheck_status`, `govulncheck_command`, `govulncheck_tool_version`, `scan_started_at`, `scan_completed_at`, `run_id` |
| `ContainerMetadata` | `root`, `image` |
| `BinaryReport` | `paths`, `size`, `go_version`, `main_package`, `main_module`, `dependencies`, `build_settings`, `sha256`, `runtime_disposition`, `layer_history`, `vulnerability_scan`, `reconciliation`, `symlinks` |
| `VulnerabilityScan` | `status`, `protocol_version`, `scanner_name`, `scanner_version`, `database`, `database_last_modified`, `go_version`, `scan_mode`, `scan_level`, `sbom`, `vulnerabilities`, `error` |
| `BinaryReconciliation` | `status`, `go_version_status`, `go_version_m`, `govulncheck_go_version`, `effective_module_inventory`, `sbom_modules` |
| `ModuleReconciliation` | `status`, `govulncheck_path`, `govulncheck_version`, `inventory_entry`, `detail` |
| `ModuleInventoryEntry` | `source`, `declared_path`, `declared_version`, `effective_path`, `effective_version` |
| `BinaryLayerObservation` | `layer_index`, `status`, `paths`, `symlinks` |

The reader accepts the current audit format only. Audits from previous formats
must be regenerated by scanning their prepared workspaces.

The remaining records likewise use their declared fields: modules, build settings,
image identity, scan statistics/issues, vulnerabilities, and findings. Producer
name/version, container root, binary Go version, build-setting keys, and
vulnerability IDs must be nonempty. Binary paths must be a nonempty list.
A binary SHA-256 is empty when hashing failed or 64 lowercase hexadecimal digits.

CGO status, container type, replacement flags, dependency summaries, vulnerability
database summaries, runtime-disposition counts, historical counts, image digest
abbreviations, final binary/path counts, and finding/SBOM status counts are derived
from saved evidence. Properties are excluded from the stored contract. Discovery
statistics retain observed traversal counts; reconciliation retains the decisions
recorded during scanning.

Diagnostics group the saved Go-version, SBOM, and finding reconciliation records
directly. New scans do not duplicate abbreviated reconciliation messages in
`issues`; operational failures remain there.

## Evidence validation

Model `__post_init__` hooks enforce nonempty values, supported states, and
SHA-256 shape during construction and `dataclasses.replace`. The reader keeps
JSON/type checks and required producer provenance. Later assignments are not
intercepted; reconstruction from
saved JSON rechecks invariants and reports the affected field path.

Runtime disposition is `runtime`, `deleted`, `replaced`, `unaccounted`, or
`unknown`; layer status is `found`, `replaced`, or `deleted`. Vulnerability scan
status is `not_run`, `disabled`, `failed`, or `complete`; tool availability is
`disabled`, `available`, or `unavailable`. Finding evidence is `module`,
`package`, or `symbol`, and reachability is `unspecified`.
Findings may include a string `symbol` containing the receiver/function name
observed in the scanner's finding trace. The field is omitted when no name was
recorded; advisory-wide symbol lists do not supply this value. Distinct observed
symbols are retained as separate observations of the same vulnerability.

Recorded module comparison statuses are `exact`, `stdlib`, `replacement`,
`representation_difference`, `mismatch`, or `unverifiable`. Finding/SBOM status
counters count those recorded comparisons on demand. They are not independently
stored or validated. Loading never reruns reconciliation or reclassifies recorded
evidence.

Raw vulnerability data is also validated:

- References contain exactly string `type` and `url` fields.
- SBOMs contain string `go_version`, a `modules` list of string `path`/`version`
  pairs, and a `roots` list of strings.
- Affected records contain string `module`/`ecosystem`, `version_ranges`, and
  `packages`. Ranges contain string `type` and `events`; each event has one or
  more string fields from `introduced`, `fixed`, `last_affected`, and `limit`.
  Packages contain string `path` and string lists `symbols`, `goos`, `goarch`.
- Vulnerabilities with no findings remain valid evidence and are retained.

Binary caches reuse the binary reader after consuming context tombstones and
restoring current paths, runtime disposition, and layer history. Cache validity
still depends on the scan ID and analysis profile. Their private record shape is
asserted in tests without production schema-version or migration machinery.
Workspace sidecars and external tool output have separate input parsers.

## Derived CVE views and batch outcomes

`CveEvidence` indexes references to a loaded audit's binary/advisory records.
It retains advisories without findings and deduplicates repeated CVE aliases
within each advisory. Paths, hashes, runtime dispositions, evidence precision,
and reconciliation counts are derived from those records. CSAF comparisons,
aggregate text/JSON/CSV reports, and advisory selection use the same index. It is not stored in
`audit.json`, and image identity assessments remain separate from local evidence.

`TargetOutcome` records a batch target's name, execution status, actual published
`audit_file` path, and failure/cancellation detail. Strict failed scans point to
their evidence under `work/`. Errors without a published audit and cancelled
targets have no audit path. These records supply `progress.tsv` and
`reports/container-summary.txt`; vulnerability findings alone do not mean execution failed.

Image identity uses `cpes` and `purls` lists for the final container,
`products` for separately supplied contexts, and `csaf_product_ids` for explicit
user selections. `sources` retains supplied final-image provenance. Each product records `name`, `component`, `version`, `release`,
`cpes`, `purls`, and `sources`. The JSON sidecar groups these under `image`,
`products`, and `csaf`; saved audits retain the typed `ImageIdentity` record.
A rootfs or layer CPE is evidence about its recorded context, not an assertion
that every binary in the final image belongs to that product.

The core does not discover image identity from vendor label files. Helper scripts
prepare the sidecar, and scans save the supplied identity. Comparisons keep
supplied `purls` and `cpes` separate from generated `derived_purls`; each generated
candidate records its source field. Derived candidates do not change audit
evidence or imply a canonical CSAF product ID.
